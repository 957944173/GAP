`uid` semantics (verified in `verl/utils/dataset/rl_dataset.py:309-315` and
`ray_trainer.py:1734`): `uid = row_dict["extra_info"]["index"]`, i.e. the **dataset row
index**, not a uuid.  The same prompt is therefore re-sampled with the same uid in later
generation batches, which is why the training-time group (and the group the filter
operates on) is `(call_index, uid)` — reproduced here exactly as in E1-0.5.

## 4. What can be done strictly, and what cannot

**Strictly (controlled, exact IDs):**

* A — same-pool retained-set relationship (`S_GAP`, `S_E1`, intersection, differences,
  Jaccard) on all three pools.
* B — group typing of the added/removed groups.
* C — sequential fixed-size batch-fill replay on any pool, because the whole candidate
  stream, its order (`call_index` + file order = `src_order`) and the filter rule are
  available.  If a pool was generated under the E1 filter, the counterfactual GAP arm is
  **right-censored** (it runs out of candidate batches before filling 32 groups); the
  `E1_0` pool is generated under the GAP filter and is therefore the **uncensored**
  counterfactual.
* D — difficulty/composition comparison of the replay cohorts.
* E — λ sweep for membership and batch-fill (reward recomputed from `em` +
  `logical_search_batches`), and the exact GRPO advantage on the selected batch.

**Only as proxy / not possible:**

* F (original GAP run composition): the original GAP training console does **not** keep
  per-group records.  It prints `std val <array>` but numpy truncates it to
  `[0. 0. 0. ... 0. 0. 0.]`, so per-rollout correctness inside a generation batch cannot be
  recovered.  Only the generation-loop counts (`len(kept_prompt_uids)` per batch, number of
  batches per optimizer step) are recoverable → `actual_run_comparison.csv` is
  OBSERVATIONAL / POLICY-CONFOUNDED.
* Response-level text analysis (e.g. re-scoring answers) is impossible: no pool stores the
  response text.
* The original GAP run's step70–120 checkpoint metadata is not needed here; no checkpoint
  was read or written.

## 5. Sanity facts recorded while auditing

* every group in all three pools has exactly **n = 8** rollouts (no size anomalies);
* rollouts are fully accounted for: `sum(group sizes) == number of rollout records` for each
  pool (147,200 / 139,520 / 641,280);
* the E1-0 audit's recorded `reward_original` equals its `em` for 147,200/147,200 records;
* the E1-A and E1-B diagnostics' recorded `reward` equals `em*(1+0.05*E)` recomputed here
  (checked implicitly by the λ=0 and λ=0.05 replays reproducing the observed filter counts
  exactly).
