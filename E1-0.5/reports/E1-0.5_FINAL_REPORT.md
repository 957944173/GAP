## 0. TL;DR — 明确结论

```
GO — 继续 step60 -> step70 new reward training (E1-A)

lambda = 0.05
cost   = logical_search_batches (assistant search round / original <wiki_search> block count)
R_i    = A_i * (1 + 0.05 * E_i)
E_i    = (Cmax - C_i)/(Cmax - Cmin)  for correct rollouts of an active group, else 0
```

理由摘要（详见第 5-7 节）：

1. 效率信号真实存在但稀疏：**95 / 18,400 = 0.5163%** 的 group 是 active。
2. 方向正确且幅度显著：efficient correct 相对 inefficient correct
   **rounds −40.3%、queries −30.4%、response tokens −35.4%**，即"更省"是真实行为，
   不是噪声。
3. **query packing 不构成主要 hack**：只有 **4/95 (4.2%)** 的 group 属于
   "rounds 减少且总 query 数不减少"的纯 packing 情形；91/95 的 group 里
   inefficient 类同时也用了更多 query。极端并行（单 block 22 个 query）全部出现在
   **错误** trajectory 上，而 `A=0` 使其奖励为 0。
4. 反事实 filter replay 已被**独立验证**：baseline 模拟逐 step 精确复现了 E1-0 中
   实际观测到的 generation batch 数（13,14,13,9,13,13,12,8,10,10 = 115）。
   新 reward 下同样 32-prompt batch 只需 **94** 次 generation batch（**−18.26%**），
   且保留 group 从 340 增加到 **424**（+84，全部为 all-correct group），无任何丢失。
5. λ 敏感性：任何 λ>0 得到**完全相同**的保留集合（λ 只影响 advantage 幅度），
   所以 λ=0.05 不是刀尖上的取值。

**必要监控项（进入 E1-A 时必须记录）**：`search_queries`、`parallel_factor`、
`structured_conversation_turns`、以及 EM 正确率。若出现
"rounds 下降但 queries/trajectory 不降"或"queries per block 持续上升"，说明
round-count reward 开始被 query packing 套利，需要改为按 query 计费或加
per-block query 上限。

## 5. Query packing 风险分析（reward hacking）

比较 active group 内的 **efficient correct**（cost = cmin，377 条）与
**inefficient correct**（cost = cmax，354 条）：

| metric | efficient | inefficient | Δ (eff − ineff) | 相对变化 |
|---|---|---|---|---|
| `logical_search_batches`（rounds） | 1.4881 | 2.4915 | **−1.0035** | −40.3% |
| `search_queries` | 2.0398 | 2.9322 | **−0.8924** | −30.4% |
| `parallel_factor`（queries/block） | 1.4770 | 1.1969 | **+0.2801** | +23.4% |
| `queries_per_round`（同义） | 1.4770 | 1.1969 | +0.2801 | +23.4% |
| `structured_conversation_turns` | 2.4881 | 3.4915 | **−1.0035** | −28.7% |
| `response_token_length` | 1,343.2 | 1,828.8 | **−485.6** | −26.6% |
| median rounds / queries | 1 / 2 | 2 / 3 | — | — |

**逐 group 判定**（`outputs/query_packing_group_detail.csv`）：

| 判定 | group 数 | 占比 |
|---|---|---|
| rounds 确实减少（eff < ineff） | 95 | 100% |
| inefficient 类 query 更多（真实省 query） | **91** | **95.8%** |
| efficient 类 query 没有减少（`eq >= iq`） | 4 | 4.2% |
| **packing_suspect = rounds 减少但总 query 未减少** | **4** | **4.21%** |
| efficient 的 queries/block 高于 inefficient | 46 | 48.4% |

**结论：不存在显著的 query-packing hack。**
证据链：

1. 效率提升是**真实的**：efficient 同时减少 rounds（−40%）、queries（−30%）、
   turns（−29%）与 response tokens（−27%）。如果它是靠把 query 塞进更少的 block，
   总 query 数应当不降甚至上升——但 91/95 的 group 里 inefficient 类用了更多 query。
2. 只有 4 个 group 属于纯 packing（成本 1 轮 vs 2 轮、query 数相同，例如
   group `2:4012`、`8:6033`、`46:105198`、`73:125800`，全部来自 nq/hotpotqa 各半），
   占比 4.2%，且这些 group 的 E 仍只是在"1 block 2 queries"与"2 blocks 2 queries"
   之间选择——语义上确实少了一次 assistant 往返，属于设计内的效率定义。
3. 极端并行出现在**错误** trajectory 上：全量 rollout 的 `parallel_factor` 最大值为
   **22**，`all_correct` 的最大值只有 **6**，`incorrect` 的最大值为 22。
   由于 `R = A·(1+λE)` 且 `A=EM`，错误轨迹的 reward 为 0，因此
   "堆 query 提高吞吐" 在当前 reward 下得不到任何回报。
4. parallel sample rate（`parallel_factor > 1`，即用过 `|` 并行）：
   efficient 50.93% vs inefficient 42.09%；但 `parallel_factor >= 2`
   （所有 block 都是并行）efficient 36.07% vs inefficient 1.98%——
   efficient 主要是"用一次并行 block 替代两次串行 round"，这正是该 reward 想鼓励的
   "用更少 round 完成任务"。

**残余风险（必须在 E1-A 监控）**：reward 只按 round 计费，理论上可以
"1 个 block 无限塞 query"来套利。当前策略没有这么做（正确轨迹 pf 最大 6，
active 组内 efficient pf 最大 3），但需要监控：
`search_queries/trajectory` 是否停止下降、`parallel_factor` 是否持续上升。
若出现，应改为按 query 计费或对 per-block query 数设上限。

产物：`outputs/query_round_analysis.csv`（对比表）、
`outputs/query_packing_verdict.json`、`outputs/query_packing_group_detail.csv`。

## 7. λ = 0.05 是否合理？

**合理，且不是敏感选择。** 两条证据：

1. **λ 敏感性扫描**（`outputs/filter_replay_lambda_sensitivity.csv`）：

| λ | baseline retained | new retained | newly added | 与 λ=0.05 保留集合相同 |
|---|---|---|---|---|
| 0.00 | 340 | 340 | 0 | 否（退化为 baseline） |
| 0.01 | 340 | 424 | 84 | **是** |
| **0.05** | **340** | **424** | **84** | — |
| 0.10 | 340 | 424 | 84 | **是** |
| 0.20 | 340 | 424 | 84 | **是** |
| 1.00 | 340 | 424 | 84 | **是** |

   原因：filter 只关心 `std(R) > 0`，任何 λ>0 只要让 active group 的 reward 出现
   差异，就得到同一保留集合。λ 决定的是 advantage 幅度，而不是"哪些 group 参与训练"。
2. **幅度可解释**：`E ∈ [0,1]`，λ=0.05 时正确轨迹的 reward 区间为 `[1.00, 1.05]`，
   即效率最多带来 5% 的 relative advantage；配合 GRPO 的
   `norm_adv_by_std_in_grpo=True`，组内排序由 E 决定、尺度由归一化决定，
   因此 λ 取小值（0.05）既足够激活全部 95 个 active group，又不会把 reward 推向
   "为省 token 而牺牲正确性"（因为 λ·E ≤ 0.05 ≪ 1，正确性 A 始终是主导项）。

**结论**：λ=0.05 合理，建议 E1-A 直接沿用；如需额外保守，可用 λ=0.01
（保留集合与 λ=0.05 完全相同，幅度更小）。

## 8. GO / NO-GO 建议

### 结论：**GO** —— 继续 `step60 -> step70 new reward` training（E1-A）

**支持 GO 的理由**

| # | 证据 | 数值 |
|---|---|---|
| 1 | 效率信号确实存在（虽然稀疏） | 95 active groups / 18,400 = 0.5163% |
| 2 | 效率方向正确、幅度真实 | efficient 比 inefficient：rounds −40.3%、queries −30.4%、tokens −26.6%、turns −28.7% |
| 3 | 不是 query-packing 套利 | 纯 packing 仅 4/95 = 4.2%；91/95 的 inefficient 同时用更多 query |
| 4 | 极端并行只出现在错误轨迹 | pf max：incorrect 22 / correct 6；A=0 使其无奖励 |
| 5 | 监督量显著增加 | retained 340 → 424（+24.7%），新增 84 个 all-correct group，0 丢失 |
| 6 | replay 已被独立验证 | baseline 逐 step 完全复现观测的 115 个 generation batch |
| 7 | 计算成本反而下降 | 同一 32-prompt batch：115 → 94 calls（−18.26%） |
| 8 | λ 稳健 | 任意 λ>0 得到同一保留集合；λ=0.05 幅度温和（≤5%） |
| 9 | 风险可监控 | 建议同时记录 queries / parallel_factor / turns / EM，套利可即时发现 |

**必须遵守的 E1-A 设计（建议）**

```
cost    = logical_search_batches
lambda  = 0.05
R_i     = A_i * (1 + 0.05 * E_i)
E_i     = (Cmax - C_i)/(Cmax - Cmin)  仅对 active group 的 correct rollout，否则 0
A_i     = EM (0/1)，原始 GAP 判定规则，不做任何修改
filter  = 保持 ray_trainer.py:1780-1781 原逻辑（std > 0）
窗口    = step60 -> step70（与 E1-0 完全对齐，便于逐 rollout 对照）
```

**风险与缓解**

| 风险 | 现状 | 缓解 |
|---|---|---|
| query packing 套利（1 block 塞很多 query） | 尚未发生（active 内 efficient pf max 3） | 监控 `parallel_factor`、`search_queries`；若上升则改按 query 计费或设 per-block 上限 |
| 过早停止搜索导致 EM 下降 | 尚未发生（efficient 组正确率由定义即为 100%） | 按 source 分别监控 EM 与多轮问题子集；λ 保持 ≤0.05 |
| 信号过稀疏、10 步看不到效果 | 每步约新增 8-9 个 group | 评估以"保留 group 构成 / rounds、query 分布"为主，不要只看总 EM；必要时延长步数（−18% 计算量可供更多步） |
| 收益集中在 hotpotqa | 新增 84 中 hotpotqa 57 / nq 27 | 报告按 source 拆分；nq 上预期变化小 |

**不建议 NO-GO**：没有任何证据支持"需要重新设计 reward"——成本定义（round）
与正确性一致、无套利主路径、λ 稳健、filter 兼容且带来真实吞吐收益。
唯一需要重新设计的触发条件是上面的监控项出现系统性 packing 或 EM 回归。

## 附录 A. 发现的问题与修复（任务约束 6）

1. **纠正 E1-0 报告中对 response 文本格式的一个错误结论。**
   E1-0 的 FINAL_REPORT §6 断言"response 中不存在 `<wiki_search>` 字面量"。
   实测：**存在**，因为 `SGLangRollout.__init__` 会把 tokenizer 的 chat template
   替换掉（`sglang_rollout.py:289`），用 `<name>arguments</name>` 形式渲染；
   而 `XMLToolParser.parse_non_stream` 会把 `a|b|c` 拆成 3 个 tool call，
   于是**每个 query 被渲染成一个独立的 `<wiki_search>` block**。
   实测 147,200 条：`resp_xml_search_batches == search_queries` 占 **99.79%**，
   而 `logical_search_batches == structured_search_rounds` 占 **100%**。
   → 结论：E1-0 审计中的 `logical_search_batches`（由 parser 的 block index 重建）
   正是任务要的"逻辑 XML block / search round 数"；response 里数出来的 block 数
   其实是 query 数，**不能**当作 round 成本。E1-0 的核心结论（reward identity、
   100% XML≡structured、group 统计）不受影响。按约束"不要覆盖 E1-0 文件"，
   此纠正只记录在 E1-0.5 的 README 与本报告，E1-0 文件未被改动。
2. **分组键核查**：uid 在本审计中不重复（每个 uid 恰好 1 个 group instance），
   所以"按 uid"与"按 (batch, uid)"等价，且每组严格 8 条，满足任务要求。
3. **replay 单位 bug**：初版把 group 当 generation batch 累加，得到 17,531 个"call"；
   修正为按 `call_index`（= 真实 generation batch，160 prompt）累加后，
   baseline 精确复现观测值 115。该修正同时成为 filter 模拟忠实度的验证。
4. **matplotlib 缺失**：`parallel-agent` 无 matplotlib，图由 `huatuo` 环境的
   子进程渲染（fallback `llama_factory`），实际使用的解释器记录在
   `outputs/summary.json["figure"]["renderer"]`，不是静默跳过。
